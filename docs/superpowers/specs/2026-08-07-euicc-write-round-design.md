# The write round: installing a profile on a card

Status: agreed 2026-08-07. Not started.

Follows [the card-read design](2026-08-06-euicc-rsp-card-read-design.md), which
covered reading. This covers the other half: the ES9+/ES8+ authentication
session and actually loading a Bound Profile Package onto the test eUICC.

Every clause number below is SGP.22 v2.6 and was read from the specification
text, not recalled.

## The goal

```
euicc build profile.vn -o profile.der   # the UPP, as today
euicc card install profile.der          # new
euicc card profiles                     # the profile is now listed
```

`install` takes an Unprotected Profile Package: a profile package in DER,
exactly what `euicc build` already writes. Binding one to a card is this
round's work; nothing about the profile format changes.

That third line is the whole point. A card that accepts a BPP and then reports
it is the only thing that proves the BPP is correct. No test we write can stand
in for it.

## Why the four BPP gaps cannot be closed first

`include/rsp.h` names four reasons no card accepts what `rsp_bpp_build`
produces today: the `'87'`/`'88'` groups are unprotected, `transactionId` is a
placeholder, `hostId` is the ICCID, and `smdpSign` is empty.

It is tempting to fix those four first. That does not work. The session keys
come from ECDH between our one-time key and `otPK.EUICC.ECKA`, and the card
does not produce that key until `ES10b.PrepareDownload` — step 6 of eight.
Until the exchange runs there is nothing to encrypt `'87'`/`'88'` with.
`transactionId` is generated by the SM-DP+, but at `InitiateAuthentication`,
and must then stay consistent through the whole session. Closing the gaps
before the exchange exists means closing them twice.

### A correction to `rsp.h`

`rsp.h` states that the real `hostId` is the eUICC's EID. That is wrong.
Annex G lists `HostID-LV` **and** `EID-LV` as separate fields of the key
derivation input. `hostId` is an identifier the SM-DP+ chooses, 1 to 16 bytes
(`OctetTo16`); §5.5.1 has the eUICC verify only `keyType` and `keyLen`, not it.

The only real requirement is consistency: the bytes in the
`controlRefTemplate` we send and the bytes in our own Annex G `SharedInfo`
must be identical, or the two sides derive different keys and everything after
that fails. Today's use of the ICCID is therefore an arbitrary choice, not a
wrong field. The implementation must keep `hostId` in **one** place so the two
uses cannot drift apart.

## Repositories and layering

A new repository, `euicc-lpa`. The dependency chain becomes:

```
euicc-tools  →  euicc-lpa  →  euicc-rsp
   (CLI)        (LPA role)    (SM-DP+ role)
```

`card info` and `card profiles` are ES10 functions — SGP.22 names the provider
"ISD-R (LPA Services)". They live in `euicc-rsp` today only because there was
nowhere else to put them. They move.

**Moves to `euicc-lpa`:** the transport (`rsp_transport_t`, PC/SC, replay,
record), `rsp_es10_send`, `rsp_card_select_isdr`, `rsp_card_read_info`,
`rsp_card_read_profiles`, `rsp_card_trusts`, all of `testdata/cards/`, and
`test_card.c`, `test_profiles.c`, `test_recording.c`, `test_pcsc.c`.

**Stays in `euicc-rsp`:** crypto (ECDH, KDF, CMAC, `rsp_protect`/
`rsp_unprotect`, the session), PKI, `rsp_sign`, `rsp_bpp_build`/
`rsp_bpp_recover`. Exactly the SM-DP+ role the repository is named for.

**New in `euicc-rsp`:** `InitiateAuthentication` (§5.6.1), `AuthenticateClient`
(§5.6.3), `GetBoundProfilePackage` (§5.6.2).

**New in `euicc-lpa`:** `GetEUICCChallenge` (§5.7.7), `AuthenticateServer`
(§5.7.13), `PrepareDownload` (§5.7.5), `LoadBoundProfilePackage` (§5.7.6),
`CancelSession` (§5.7.14), `DeleteProfile` (ES10c §5.7.18), and the sequencing
that drives them.

The move is the riskiest part of this round: it touches working, tested code
and delivers no feature. It is therefore its own completed step, before any new
work.

Its acceptance criterion needs care, because the tests themselves move. It is
not "235 still pass in `euicc-rsp`" — that number will drop by design. It is:
**no test is deleted, and the total across all repositories does not fall below
334** (235 + 99). Every test that moves keeps its assertions unchanged; a test
that becomes awkward to move is still moved, not dropped.

`euicc-tools` loses its direct dependency on `euicc-rsp`. The archive trick
(`build/librsp-full.a`) moves with it, and open finding J — the missing guard
against duplicate asn1c symbols such as `UICCCapability` — gets worse, not
better: three repositories will carry generated ASN.1 into one binary. The
guard should land as part of the move.

## The exchange

| # | Who | Call | Yields |
|---|---|---|---|
| 1 | lpa → card | `GetEUICCInfo` §5.7.8 | `euiccInfo1` |
| 2 | lpa → card | `GetEUICCChallenge` §5.7.7 | the challenge |
| 3 | lpa → dp | `InitiateAuthentication` §5.6.1 | `transactionId`, `serverSigned1`, `serverSignature1`, CERT.DPauth |
| 4 | lpa → card | `AuthenticateServer` §5.7.13 | `euiccSigned1`, `euiccSignature1`, CERT.EUICC, CERT.EUM |
| 5 | lpa → dp | `AuthenticateClient` §5.6.3 | ProfileMetadata, `smdpSigned2`, `smdpSignature2`, CERT.DPpb |
| 6 | lpa → card | `PrepareDownload` §5.7.5 | `euiccSigned2` carrying **otPK.EUICC.ECKA**, `euiccSignature2` |
| 7 | lpa → dp | `GetBoundProfilePackage` §5.6.2 | the finished BPP |
| 8 | lpa → card | `LoadBoundProfilePackage` §5.7.6 | `ProfileInstallationResult` |

Step 6 is the hinge. Nothing cryptographic about the BPP can exist before
step 7.

### Where the four gaps are filled

- `transactionId` — generated by the SM-DP+ at step 3, carried through. §5.5.1
  requires it to be unique within the scope and lifetime of each SM-DP+,
  explicitly as protection against replayed `CancelSession` messages.
- EID — arrives in `euiccSigned1` at step 4, goes into the Annex G
  `SharedInfo`.
- `hostId` — a constant we choose, the same bytes in the CRT and in
  `SharedInfo`, held in one place. See the correction above.
- `smdpSign` — per §5.5.1, computed with **SK.DPpb** (not DPauth) over
  `remoteOpId ‖ transactionId ‖ controlRefTemplate ‖ smdpOtpk ‖ euiccOtpk`.
  Including `euiccOtpk` is what lets the card authenticate the server.

### The ES9+ boundary

Every ES9+ message is a real structure, DER in and DER out, but `euicc-lpa`
calls the functions directly. There is no network. This costs almost nothing
extra because the structures have to exist anyway — `smdpSigned2` and
`smdpSignature2` are defined over them.

§6.5 binds ES9+ as JSON over HTTPS with base64-encoded ASN.1 inside. That
envelope is exactly the layer being left out. A future HTTP server adds §6.5 on
top without changing any of these functions.

### Protecting the BPP

Table 4 in §2.5.4 gives the construction precisely:

- `'87'` (ConfigureISDP) — encrypted **and** MAC'd, with S-ENC and S-CMAC
- `'88'` (StoreMetadata) — MAC'd only, explicitly not encrypted
- `'86'` (the profile) — encrypted and MAC'd

All three advance the same chain, in that order. `rsp_protect` implements
`'86'` only, so this round adds a MAC-only variant and gets the ordering right.

## How this is proved

A write session cannot be replayed the way a read session can: it is one-shot,
it changes the card, and one-time keys make the bytes differ every run. Three
things fix that.

### Deterministic ECDSA

`rsp_sign` uses `mbedtls_ecdsa_sign` with a globally seeded DRBG — plain,
randomised ECDSA. No recording can ever replay byte-identically while that is
true.

Switch to RFC 6979 (`mbedtls_ecdsa_sign_det_ext`). This is the safer choice on
its own merits, independent of testing: with a random `k`, one repeated or
biased nonce reveals SK.DPpb. Afterwards a signature is a pure function of key
and message, and signatures stop being a source of nondeterminism.

This lands alone, before anything else, with its own evidence: the same message
and key sign identically twice, and the signature still verifies.

### The two remaining random values become parameters

Only `otSK.DP.ECKA` and `transactionId` are left. Both are inputs to the flow,
so they become arguments of `InitiateAuthentication` and
`GetBoundProfilePackage` — not a hidden RNG hook. Production generates them
fresh; the test passes fixed values. There is no global state and no default
value, so there is no test path that can be shipped by accident.

### No eUICC simulator

An earlier draft of this design proposed a simulated ISD-R for the failure
cases. It was dropped. A simulator refuses exactly what we tell it to refuse —
the self-consistency trap this project has already been caught by once, when
`rsp_bpp_recover` was tested only against `rsp_bpp_build`.

The card's error responses are specified DER structures, so they are built by
hand with the generated encoder instead — the pattern already used twice for
`omnikey-profiles-error.log` and `synthetic-profiles-bad-request.log`. Cheaper,
honest about what it proves, and it checks the thing that matters: that a
refusal is reported as a refusal and never as success.

### So the evidence is

1. **One recorded real installation.** These exact bytes made a real eUICC
   accept a profile, and `card profiles` then listed it.
2. **Hand-built error fixtures** for each `ProfileInstallationResult` failure
   and for the aborts at steps 4 and 6.
3. **Mutations.** Every new assertion must fail under the matching mutation, or
   it does not count.

### Secret discipline

The recorded installation plus the committed test `otSK` yields the profile in
clear text: anyone who clones the repository can decrypt it. That is
unavoidable if replay is to be deterministic. The installed test profile must
therefore carry obviously worthless key material, as `profile.vn` already does,
and the fixture README must say so outright rather than leaving the reader to
work it out.

An installation can only be recorded once per ICCID. Re-recording means
deleting first, which is why `DeleteProfile` is in this round.

## Command surface

```bash
euicc card install profile.der
euicc card delete 8944058925001234567F
```

Both take the same flags as the existing card commands: `--reader`, `--replay`,
`--record`, `--json`.

The exit contract is the project's usual one.

`install` — **0** the profile is installed and `ProfileInstallationResult` says
so. **1** the eUICC answered and refused: signature rejected, out of memory,
ICCID already present, profile policy violated, or an abort at step 4 or 6.
**2** the question could not be asked at all.

`delete` — **0** deleted. **1** the card refused, with the reason named:
`iccidOrAidNotFound`, `profileNotInDisabledState`, `disallowedByPolicy`.
**2** could not be asked.

The difference between 1 and 2 is worth more here than anywhere else in the
project. For an installation, "refused" means the card and the server talked
and the card said no; "could not be asked" means nothing happened at all.
Confusing them sends the reader looking in the wrong place.

### A failed load blocks the next one

§5.5.1: `InitialiseSecureChannel` is rejected while an RSP session is already
ongoing. §5.7.14 `CancelSession` discards it, and `CancelSessionReason` has
`loadBppExecutionError(5)` for exactly this case.

`install` cancels its own session on any failure it can still act on. It
**cannot** clear a session stranded by something else: `CancelSession` requires
the matching `transactionId`, which a fresh run does not know. If the tool dies
mid-installation, the card has to be re-seated. This is documented rather than
left for the user to discover.

## Out of scope, with reasons

- **HTTPS and the JSON binding (§6.5).** The call is in-process. Later a
  transport in front, with no change to these functions.
- **Notifications (§5.7.9–5.7.11, ES9+.HandleNotification).** The eUICC
  generates as many as `notificationConfigurationInfo` in the metadata
  configures. The test profile configures none, so none are generated. This is
  a cut with a specification basis, not a hole.
- **Confirmation code.** Optional in the flow, meaningless for a local tool.
- **`secondSequenceOf87` / ReplaceSessionKeys.** Optional per Table 4. The
  `'86'` segments are protected with the session keys, not with separate
  profile protection keys.
- **EnableProfile and DisableProfile (§5.7.16/5.7.17).** They answer `91xx` —
  success with a REFRESH pending — which the transport does not yet understand.
  Note that a profile must be disabled before it can be deleted
  (`profileNotInDisabledState`), so this limit is real: a profile that somehow
  gets enabled cannot be removed by this round's tooling.
- **Multiple certificate issuers.** One test CI, one chain.
- **Activation codes and SM-DP+ address discovery.** The tool takes a file
  path.

## Order of work

The order is forced, not chosen.

1. **The move.** Transport and ES10 to `euicc-lpa`, no behaviour change, plus
   the finding J guard. Nothing new is built until the same 235 and 99 tests
   pass again, because otherwise a later failure cannot be attributed to either
   the move or the new code.
2. **Deterministic ECDSA**, alone, with its own evidence.
3. **The ES9+ structures and the three SM-DP+ functions.**
4. **The ES10b functions in `euicc-lpa`.**
5. **`'87'`/`'88'` protection and the four gaps.**
6. **The sequencing and `LoadBoundProfilePackage` segmentation.**
7. **CLI: `install`, `delete`, session cancellation.**
8. **The proof:** record against the real card, hand-build the error fixtures,
   hold every new assertion to a mutation.

Steps 1 and 2 are prerequisites for everything. The rest follows the data: the
exchange before the BPP, because the BPP is made of what the exchange produces.

### This is two plans, not one

Step 1 is a migration with its own acceptance criterion and no feature to show
for it. Steps 2 to 8 are the write path. They should be planned and executed
separately, in that order:

- **Plan A — the move.** Create `euicc-lpa`, relocate the transport, ES10, the
  fixtures and their tests, rewire `euicc-tools`, add the finding J guard.
  Done when no test has been deleted and the total across repositories is at
  least 334.
- **Plan B — the write path.** Everything from deterministic ECDSA to the
  recorded installation.

Writing Plan B before Plan A has landed would mean planning against a file
layout that does not exist yet. Plan B is written after the move is done.

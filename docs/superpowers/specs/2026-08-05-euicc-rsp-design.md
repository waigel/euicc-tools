# euicc-rsp: load a profile onto a test eUICC

Status: agreed 2026-08-05. Not started.

## The goal

`euicc flash profile.vn` puts a profile onto a test eUICC in a card reader.
Later, a visual surface builds and flashes profiles; it drives the same
command, the way the VS Code extension drives `euicc check --json` today.

A profile package fails on the way to a card in a third way, beyond the two
that `euicc check` already reports. The package can be correct and still not
install, because the card refuses anything it cannot authenticate. This
project supplies what the card demands: the cryptographic role of an SM-DP+.

## What this is not

Not a server. There is no HTTPS, no ES2+, no SM-DS, no activation code, and
no operator interface. A real SM-DP+ serves remote devices over the network;
this serves a card in a reader over PC/SC. An ES9+ front end can sit on this
library later, but nothing here anticipates it.

Not for production cards. The certificates are the published GSMA SGP.26 test
material. A production eUICC rejects them, and a production profile must not
be loaded with them.

## Decisions

| Question | Decision |
| --- | --- |
| Where the truth lives | A C library, `euicc-rsp`, consumed by `euicc-tools` as a submodule. The CLI is the only interface. A later UI is a client of the CLI. |
| Card standard | SGP.22 consumer. Certificate-based trust, ES9+/ES8+ messages, SCP03t. |
| Repository boundary | The SM-DP+ role and the card transport, in one repository. |
| Trust anchor | The GSMA SGP.26 test CI. Its private key is published, so DPauth and DPpb certificates are minted locally. |
| How correctness is proven | Specification first, against SGP.26 vectors. No foreign implementation is used as an oracle. |
| Crypto library | mbedTLS, as a submodule. |

## Architecture

Four components with one purpose each, and one thin layer that orders them.

| Component | Purpose | Knows nothing about |
| --- | --- | --- |
| `rsp_codec` | The RSP ASN.1 module of SGP.22 Annex H, generated by asn1c through the same pipeline as `euicc-schema`. Encodes and decodes the messages. | crypto, the card |
| `rsp_crypto` | Key agreement, session key derivation, SCP03t segmentation with encryption and MAC, certificate verification, signature creation. Pure functions over buffers. | the card, the clock, the filesystem |
| `rsp_card` | The transport: PC/SC, ISD-R select, APDU chaining, the ES10b commands. Behind an interface, so a test can inject a recorded card. | crypto, certificates |
| `rsp_pki` | Mints DPauth and DPpb certificates under the SGP.26 test CI. A setup-time concern, not a per-download one. | the card, the flow |

Above them, `rsp_flow` sequences the procedure and holds no logic of its own:
ask the card, compute, load the card. It is the only file that needs the
sequence diagram of the specification open, and it must fit on one screen.

Dependencies point one way. `rsp_flow` uses the four components. Among the
components there is exactly one edge: `rsp_crypto` uses `rsp_codec`, because
protecting a message means encoding it first. Every other pair is unaware of
each other, and `rsp_card` never sees a key.

The split follows where the faults live. Calculation faults live in the
crypto, so it must be testable with no hardware and no clock. Device quirks
live in the card layer, so it must be replaceable by a recording.

mbedTLS supplies everything needed: P-256 for ECDH and ECDSA, AES-CBC,
AES-CMAC, and X.509 both read and written. OpenSSL is more widespread, but
macOS ships no headers for it, and the promise of this family is that nothing
has to be installed.

## The flow

Because the tool is both the LPA and the SM-DP+, the network protocol becomes
a chain of function calls.

| Step | What happens | Component |
| --- | --- | --- |
| 1-3 | Open the card, select the ISD-R, `GetEUICCChallenge`, `GetEUICCInfo` | `rsp_card` |
| 4 | Build `serverSigned1` and sign it with SK.DPauth | `rsp_crypto` |
| 5 | `AuthenticateServer`. The card verifies our chain against its CI and answers with its signature, its certificate, and `eUICCInfo2` | `rsp_card` |
| 6 | Verify the signature of the card and its EUM chain | `rsp_crypto` |
| 7-8 | Sign `smdpSigned2`, then `PrepareDownload`. The card returns its one-time public key | both |
| 9 | ECDH with our one-time key. Derive S-ENC, S-MAC, and the initial MAC chaining value | `rsp_crypto` |
| 10 | Build the BPP: `initialiseSecureChannel`, `configureISDP`, `storeMetadata`, then the protected UPP segments | `rsp_crypto`, `rsp_codec` |
| 11-12 | Send the BPP segment by segment with `LoadBoundProfilePackage`, read the `ProfileInstallationResult` | `rsp_card` |

The exact composition of `serverSigned1` and `smdpSigned2` comes from
SGP.22 §3.1.2 and §5.7 at implementation time. This table states the shape,
not the bytes.

Steps 4 to 10 are pure calculation. Because `rsp_card` sits behind an
interface, the answers of a real card are recorded once and replayed. The
whole crypto path then runs in CI with no reader attached.

## The commands

The exit contract of the family holds: 0 for done, 1 for the card said no,
2 for we could not answer.

```sh
euicc card info                      # EID, versions, accepted CI key ids
euicc card profiles                  # what is already installed
euicc pki init --out ~/.euicc/pki    # DP certificates under the SGP.26 test CI, once
euicc flash profile.vn               # build, check, bind, load
euicc flash profile.vn --dry-run     # the handshake and the BPP, but write nothing
```

`card info` comes first on purpose. It answers at the real card what this
design assumes: which CI key ids the card accepts.

`flash` takes `.vn` and `.der` alike, and runs `check` before it writes to
hardware. A profile that breaks the rules does not reach a card unasked.
`--no-check` overrides this, because "does the card reject a broken profile?"
is a legitimate test.

Every command takes `--json` and emits one object, the way `check --json`
does. If the later surface needs a progress bar, it gets an event stream
then, not on suspicion.

## Failures

The card answers a calculation fault as tersely as a wrong certificate. One
swapped byte in a session key produces a MAC failure in the first segment,
and what comes back is a status word. Guessing from there costs days.

So a failure must be nameable, the way a rule failure names its clause.

- **Exit 2, we could not answer.** No reader, no card, no ISD-R, missing
  certificate material. These are setup faults, and the message names the
  fix, as the stale-binary warning does today.
- **Exit 1, the card said no.** It answered, and the answer is no. The error
  enums of `AuthenticateServer` and the `errorReason` of the
  `ProfileInstallationResult` become sentences with a clause.
  `invalidCertificate` reads as "the card rejected our DP chain; it accepts
  these CI key ids: ...", not as `0x6A80`.
- **Exit 0.** Installed, with the ICCID and the result.

Against the opaque case, the tool checks itself before it sends: it decrypts
the PPP it just built with the same session keys and compares the result
against the UPP. A mismatch is our fault, and it is reported without touching
the card. This costs milliseconds and turns the most expensive failure into
the cheapest.

Two more rules. When loading breaks off between segments, the report names
which segment and what the card said, and the ISD-P is **not** cleaned up
automatically; the report says that it needs cleaning. Private DP keys and
session keys never appear in output, in `--json`, or in a log.

## Tests

Four levels, three of them without hardware.

| Level | What it proves | In CI |
| --- | --- | --- |
| Vectors | ECDH and AES-CMAC against published NIST values; the certificate chain against the SGP.26 material. The key derivation of SGP.22 has no published vector and is pinned to its own output until a card settles it | yes |
| Round trip | UPP to BPP, decrypt it again, compare with `euicc diff`. Catches segmentation, padding, MAC chaining | yes |
| Recorded card | A captured handshake is replayed and the whole flow computes through. The recording plus the expected BPP is the golden vector | yes |
| Real card | `make check-card`, only with a reader attached. It refuses to run in CI instead of passing silently | no |

The first BPP that a card accepts is frozen as the golden vector. From then
on every change is differential against something that demonstrably worked.
This is how the spec-first path compensates for having no foreign oracle: the
oracle becomes our own proven output.

Every test must be able to fail. Flip a byte in a session key and the round
trip must go red, or it proves nothing.

The first candidate for real hardware is `examples/profile.vn`, the complete
package that `euicc check -s` accepts without a finding.

## Order of work

1. `rsp_codec`: the RSP ASN.1 module through asn1c. Mechanical, and it shows
   how much of the existing codec pipeline carries over.
2. `rsp_pki` and the vector tests: mint DP certificates, pin the primitives.
3. `rsp_crypto`: session keys, SCP03t, the BPP. Verified by the round trip.
4. `rsp_card`: PC/SC and ES10b, with the recording interface from the start.
5. `rsp_flow` and the CLI commands in `euicc-tools`.
6. The real card.

Steps 1 to 3 need no hardware. Step 4 is the first that does.

## Open points

- The SGP.26 test key material has to be committed. It is published, so this
  is allowed, but the README must state plainly that it works on test cards
  only and never in production.
- Whether the card accepts the GSMA test CI is assumed here and is verified
  by `card info` before step 3 is worth finishing.
- mbedTLS 3.x made structure fields private and renamed interfaces. The
  submodule is pinned to one version, and the version is named in the build.
